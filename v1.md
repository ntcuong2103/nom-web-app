# v1 Implementation Plan

Build v1 around one goal: a user can upload images, annotate rectangles, edit labels, review history, and export YOLO data.

Keep everything else secondary until that loop works end to end.

## Step 0 - Freeze the v1 scope

### Required for v1

* login
* dataset creation
* image upload
* image browser
* annotation editor with rectangle boxes
* label editing
* save/load annotations
* annotation audit history
* basic image and annotation filters
* YOLO export
* group review with bulk approve

### Defer until after the core loop works

* clustering
* background workers
* Redis
* permanent crop storage
* enterprise auth or SSO
* advanced search
* annotation versioning beyond event history

## Step 1 - Start with the simplest architecture

Use three runtime pieces at first:

1. frontend app
2. backend API
3. database

For local development, store uploaded images on the filesystem behind a small storage abstraction. Do not add S3, MinIO, Redis, or background workers until the app needs them.

Recommended layout:

* `frontend/` - Next.js app
* `backend/` - API app
* `infra/` - optional Docker Compose and env examples
* `storage/` - local uploaded image files

## Step 2 - Initialize only the tools needed now

Frontend:

* Next.js
* TypeScript
* Tailwind
* TanStack Query
* react-konva

Backend:

* LitServe or a simple Python API service
* request/response schema validation
* SQLAlchemy 2.x
* Alembic
* PostgreSQL driver
* password hashing
* JWT access tokens

Do not add Zustand unless local state becomes hard to manage. Start with component state and TanStack Query cache.

## Step 4 - Build the API foundation

Implement the API in the same order the product workflow needs it.

### 4.1 Authentication

Use a simple local login flow:

* local users in the database
* password hashing
* JWT access tokens
* role field on `users`

### 4.2 Dataset endpoints

* `POST /datasets`
* `GET /datasets`
* `GET /datasets/{id}`
* `PATCH /datasets/{id}`

### 4.3 Image endpoints

* `POST /datasets/{id}/images`
* `GET /datasets/{id}/images`
* `GET /images/{id}`
* `GET /images/{id}/file`

Store image files outside Postgres. Keep only metadata and storage keys in the database.

### 4.4 Annotation endpoints

* `GET /images/{id}/annotations`
* `POST /images/{id}/annotations`
* `PATCH /annotations/{id}`
* `DELETE /annotations/{id}`

Every create, update, and delete should insert one `annotation_events` row.

Recommended `event_type` values for v1:

* `user_created`
* `user_moved`
* `user_resized`
* `user_relabeled`
* `user_deleted`

### 4.5 Audit-read endpoints

* `GET /annotations/{id}/events`
* `GET /images/{id}/events`

The image-level endpoint is useful for the editor history panel.

Build enough shell to support the main workflow:

## Step 6 - Build the annotation editor as the first vertical slice

The editor is the core of v1. Make it usable before adding clustering or job infrastructure.

Minimum editor behavior:

* load image
* load existing annotations
* draw rectangle
* select rectangle
* move rectangle
* resize rectangle
* edit label
* delete rectangle
* save changes
* show image-level history

Use react-konva for the annotation layer.

Implementation order:

1. read-only image display
2. load existing annotations
3. draw rectangle locally
4. save new rectangle to API
5. select and list rectangles
6. move/resize rectangle
7. edit label
8. delete rectangle
9. show history panel
10. add keyboard shortcuts

At this point, v1 has a real usable core.

## Step 7 - Add basic filters

Keep filters structured and database-backed:

* image filename
* annotation label
* annotation status

Use these in:

* dataset image browser
* annotation list/sidebar

Do not add a dedicated search engine in v1.

## Step 8 - Add YOLO export

Implement export after annotation save/load is reliable.

Simple v1 workflow:

1. user requests export for a dataset
2. API generates YOLO files from current annotations
3. API writes a zip archive to local storage
4. frontend shows a download link

This can be synchronous at first. Add an `export_jobs` table and background worker only if export takes too long for normal request/response.

## Step 9 - Add crop previews

Add one derived-image endpoint:

* `GET /images/{image_id}/crop?x=...&y=...&w=...&h=...&size=128`

This endpoint:

* loads the original uploaded image
* crops the requested box
* optionally resizes it
* returns the thumbnail image

Do not store crops permanently in v1. Crops are derived from the source image and annotation geometry.

## Step 10 - Add group review

Bulk import (Step 8, plus the folder-path import added after v1) can add thousands of
annotations at once, most needing human review. Reviewing them one image at a time in
the annotation editor does not scale. Add a review workflow that groups annotations
across a dataset instead of by image.

Goal: let a reviewer filter to a slice of annotations across the whole dataset and
approve them together, instead of opening each image individually.

Filters:

* character code (`label`)
* source folder (the per-volume path an image was imported from - requires storing that
  on `images`, since only the filename is kept today)
* status (`active` / `review` / `deleted`)

Workflow:

1. reviewer picks a dataset and a filter combination
2. page shows a grid of cropped bounding boxes matching the filter (reuse the existing
   crop endpoint), with the total matching count shown up front
3. reviewer selects individual boxes, selects everything currently loaded, or selects
   all results matching the filter - a single character can match thousands of
   annotations, so "select all" must be a server-side bulk action scoped by filter, not
   a client-side list of every id
4. reviewer group-approves the selection in one action, moving `status` from `review`
   to `active`

New pieces needed:

* an `images.source_folder` column (or equivalent), populated by the folder-path
  import, to support the folder filter
* a filtered annotation-list endpoint scoped to a dataset rather than a single image,
  e.g. `GET /datasets/{id}/annotations?label=...&folder=...&status=...`
* a bulk-approve endpoint that accepts either an explicit list of annotation ids or the
  same filter (for the "select all matching" case), e.g.
  `PATCH /datasets/{id}/annotations/approve`
* a review grid page in the frontend, distinct from the single-image annotation editor

Keep this filter-only for v1: no clustering or similarity grouping. That belongs to the
broader roadmap's clustering/search work, built on top of these filters later.

### Also worth considering

* **Bulk reject alongside bulk approve** - the same selection mechanism should be able
  to move a batch to `deleted`, not just `active`; a review queue needs both directions.
* **Bulk relabel** - a reviewer scanning one character's boxes will sometimes find a
  batch that was mislabeled entirely; let them relabel the selection in one action
  instead of one at a time.
* **Sort by confidence, not just filter by status** - `selection_flag` from the
  folder-path import is a real confidence signal; sorting the grid lowest-confidence
  first surfaces the boxes most likely to need correction rather than reviewing in
  arbitrary order.
* **Confirm before a large bulk action** - show the match count and require explicit
  confirmation before approving/rejecting/relabeling a "select all matching" batch,
  since it can silently touch thousands of rows.
* **Keyboard-driven review** - this is a repetitive, high-volume task; arrow keys to
  move focus, space to toggle selection, and a single key to approve/reject the
  focused box will matter more here than in the single-image editor.
* **Undo the last bulk action** - a mis-scoped filter approving/rejecting/relabeling
  thousands of rows at once is the kind of mistake worth a one-step undo for, even if
  full annotation versioning stays out of scope.

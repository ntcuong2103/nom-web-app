# v1 Implementation Plan

Build v1 around one goal: a user can upload images, annotate rectangles, edit labels, review history, and export YOLO data.

Keep everything else secondary until that loop works end to end.

## Step 0 - Freeze the v1 scope

### Required for v1

* login
* dataset creation
* image upload
* image browser
* annotation editor with rectangle boxes
* label editing
* save/load annotations
* annotation audit history
* basic image and annotation filters
* YOLO export

### Defer until after the core loop works

* clustering
* background workers
* Redis
* permanent crop storage
* enterprise auth or SSO
* advanced search
* annotation versioning beyond event history

## Step 1 - Start with the simplest architecture

Use three runtime pieces at first:

1. frontend app
2. backend API
3. database

For local development, store uploaded images on the filesystem behind a small storage abstraction. Do not add S3, MinIO, Redis, or background workers until the app needs them.

Recommended layout:

* `frontend/` - Next.js app
* `backend/` - API app
* `infra/` - optional Docker Compose and env examples
* `storage/` - local uploaded image files

## Step 2 - Initialize only the tools needed now

Frontend:

* Next.js
* TypeScript
* Tailwind
* TanStack Query
* react-konva

Backend:

* LitServe or a simple Python API service
* request/response schema validation
* SQLAlchemy 2.x
* Alembic
* PostgreSQL driver
* password hashing
* JWT access tokens

Do not add Zustand unless local state becomes hard to manage. Start with component state and TanStack Query cache.

## Step 3 - Create the minimum database schema

Start with only the tables needed for the manual annotation workflow:

* `users`
* `datasets`
* `images`
* `annotations`
* `annotation_events`

### `users`

* id
* email
* password_hash
* role
* created_at

### `datasets`

* id
* name
* description
* created_by
* created_at

### `images`

* id
* dataset_id
* storage_key
* filename
* width
* height
* uploaded_by
* created_at

### `annotations`

* id
* image_id
* x
* y
* w
* h
* label
* status
* created_by
* updated_by
* created_at
* updated_at

### `annotation_events`

* id
* annotation_id
* actor_user_id
* event_type
* old_value_json
* new_value_json
* created_at

This is enough for v1 audit history. Do not model full annotation versioning yet.

## Step 4 - Build the API foundation

Implement the API in the same order the product workflow needs it.

### 4.1 Authentication

Use a simple local login flow:

* local users in the database
* password hashing
* JWT access tokens
* role field on `users`

### 4.2 Dataset endpoints

* `POST /datasets`
* `GET /datasets`
* `GET /datasets/{id}`
* `PATCH /datasets/{id}`

### 4.3 Image endpoints

* `POST /datasets/{id}/images`
* `GET /datasets/{id}/images`
* `GET /images/{id}`
* `GET /images/{id}/file`

Store image files outside Postgres. Keep only metadata and storage keys in the database.

### 4.4 Annotation endpoints

* `GET /images/{id}/annotations`
* `POST /images/{id}/annotations`
* `PATCH /annotations/{id}`
* `DELETE /annotations/{id}`

Every create, update, and delete should insert one `annotation_events` row.

Recommended `event_type` values for v1:

* `user_created`
* `user_moved`
* `user_resized`
* `user_relabeled`
* `user_deleted`

### 4.5 Audit-read endpoints

* `GET /annotations/{id}/events`
* `GET /images/{id}/events`

The image-level endpoint is useful for the editor history panel.

## Step 5 - Build the frontend shell

Build enough shell to support the main workflow:

* login page
* dataset list page
* dataset detail page
* image browser
* annotation editor page
* export page

Recommended structure:

* `app/(auth)/login`
* `app/datasets`
* `app/datasets/[datasetId]`
* `app/images/[imageId]/annotate`
* `app/datasets/[datasetId]/export`
* `components/layout`
* `components/annotation`
* `lib/api`
* `lib/types`

Get routing, auth state, layout, and API calls working before polishing the annotation canvas.

## Step 6 - Build the annotation editor as the first vertical slice

The editor is the core of v1. Make it usable before adding clustering or job infrastructure.

Minimum editor behavior:

* load image
* load existing annotations
* draw rectangle
* select rectangle
* move rectangle
* resize rectangle
* edit label
* delete rectangle
* save changes
* show image-level history

Use react-konva for the annotation layer.

Implementation order:

1. read-only image display
2. load existing annotations
3. draw rectangle locally
4. save new rectangle to API
5. select and list rectangles
6. move/resize rectangle
7. edit label
8. delete rectangle
9. show history panel
10. add keyboard shortcuts

At this point, v1 has a real usable core.

## Step 7 - Add basic filters

Keep filters structured and database-backed:

* image filename
* annotation label
* annotation status

Use these in:

* dataset image browser
* annotation list/sidebar

Do not add a dedicated search engine in v1.

## Step 8 - Add YOLO export

Implement export after annotation save/load is reliable.

Simple v1 workflow:

1. user requests export for a dataset
2. API generates YOLO files from current annotations
3. API writes a zip archive to local storage
4. frontend shows a download link

This can be synchronous at first. Add an `export_jobs` table and background worker only if export takes too long for normal request/response.

## Step 9 - Add crop previews

Add one derived-image endpoint:

* `GET /images/{image_id}/crop?x=...&y=...&w=...&h=...&size=128`

This endpoint:

* loads the original uploaded image
* crops the requested box
* optionally resizes it
* returns the thumbnail image

Do not store crops permanently in v1. Crops are derived from the source image and annotation geometry.

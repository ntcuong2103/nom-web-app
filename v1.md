# Step 0 — Freeze the v1 scope

Before coding, write down what v1 includes and what it excludes.

For v1, I recommend this exact scope:

* login
* dataset creation
* image upload
* image browser
* annotation editor with rectangle boxes
* label editing
* save/load annotations
* audit log for user edits
* approval by user
* clustering page that shows grouped cropped regions
* simple search/filter
* YOLO export


# Step 1 — Create the baseline architecture

Set up four runtime components from day one:

1. frontend app
2. backend API
3. relational database
4. object storage

A fifth component, background jobs, should be added very early even if only one task uses it. Next.js supports modern App Router architecture and can be deployed as a Node.js server or Docker container, while FastAPI is a production-oriented Python web framework. Dramatiq is a Python background task library that supports Redis as a broker, which matches the stack we discussed. ([Next.js][1])

Recommended layout:

* `frontend/` → Next.js app
* `backend/` → FastAPI app
* `worker/` → Dramatiq jobs
* `infra/` → Docker Compose, Nginx, env files
* `storage/` → local dev volumes

# Step 4 — Build the backend foundation first

Implement the backend in this order:

## 4.1 Authentication

Use a simple login flow first:

* local users in database
* password hashing
* JWT access tokens
* role field on user

Do not introduce enterprise SSO in v1 unless you already need it.

## 4.2 Dataset endpoints

Create:

* `POST /datasets`
* `GET /datasets`
* `GET /datasets/{id}`
* `PATCH /datasets/{id}`

## 4.3 Image upload endpoints

Create:

* `POST /datasets/{id}/images`
* `GET /datasets/{id}/images`
* `GET /images/{id}`

Store page images in object storage, not in Postgres.

## 4.4 Annotation CRUD

Create:

* `GET /images/{id}/annotations`
* `POST /images/{id}/annotations`
* `PATCH /annotations/{id}`
* `DELETE /annotations/{id}`

Every create/update/delete should also insert into `annotation_events`.

## 4.5 Approval endpoints

Create:

* `POST /annotations/{id}/approve`
* `POST /images/{id}/approve-all`

Keep the approval model simple:

* approved by user
* approved timestamp

# Step 6 — Build the annotation editor as the first vertical slice

This is the core of the system. Make it usable before adding clustering.

The editor needs:

* image load
* zoom and pan
* draw box
* select box
* resize/move box
* edit label
* delete box
* save changes
* approval action
* event history panel

Use react-konva for the annotation layer. Konva’s React integration is specifically intended for interactive canvas applications and documents shapes, events, drag/drop, and responsive canvas patterns relevant to editors like this. ([Next.js][1])

The best implementation order is:

1. read-only image display
2. draw rectangle
3. list annotation boxes
4. save to backend
5. edit box geometry
6. edit label
7. approval button
8. keyboard shortcuts

At this point, you already have a real v1 core.

# Step 7 — Add image cropping for preview, but do not store crops yet

For v1 clustering UI, do not store every crop as a permanent file.

Instead, build one backend endpoint such as:

* `GET /images/{image_id}/crop?x=...&y=...&w=...&h=...&size=128`

This endpoint:

* loads the original image from object storage
* crops the requested box
* optionally resizes it
* returns a thumbnail image

That gives you immediate support for:

* annotation previews
* search result thumbnails
* cluster galleries

This is the right v1 tradeoff because crop images are derived from the source image plus bbox and would otherwise create a synchronization problem when annotations change.

# Step 8 — Build the clustering feature as a read-only workflow first

For v1, clustering should not be interactive ML management. Make it a simple workflow:

1. backend receives a clustering request for a dataset
2. worker loads annotation crops in memory
3. worker computes embeddings or features (not yet)
4. worker assigns cluster ids (randomly assigned)
5. worker stores `clusters` and `cluster_members`
6. frontend shows cluster gallery with crop previews

This is exactly where background jobs become useful. Dramatiq is designed for background task processing and supports Redis-backed brokering, which fits batch clustering work. ([Dramatiq][3])

For v1 UI, each cluster page only needs:

* cluster id
* number of members
* grid of cropped previews
* click preview to open original image annotation page

That is enough to make clustering operational.

# Step 9 — Add basic search and filters

Do not overbuild search in v1.

Implement only structured search in Postgres:

* dataset
* image filename
* label
* status
* approved/unapproved

Pages:

* dataset image browser filters
* annotation list filters
* cluster member filters

This will already cover most workflow needs. A dedicated search engine can come later.

# Step 10 — Add YOLO export

After annotation and clustering work, implement export.

Workflow:

1. user requests export for dataset
2. backend creates `export_job`
3. worker generates YOLO annotation files
4. worker writes archive to object storage
5. frontend shows downloadable artifact

Do export asynchronously because large datasets can take time.

# Step 11 — Add audit history visibility

You already store `annotation_events`; now surface it.

In the annotation page, add a history side panel:

* created
* moved
* resized
* relabeled
* deleted
* approved

This is very important because audit is one of your distinguishing requirements. It also gives you debugging ability during development.

# Step 12 — Add background jobs properly

At first you may only use the worker for clustering and export. That is enough.

Initial job types:

* `cluster_dataset`
* `export_dataset_yolo`
* optional `generate_dataset_stats`

Dramatiq’s docs describe Redis as a supported broker, and Next.js’s docs support Docker/self-hosted deployment, so this stack works well under Docker Compose for a small team setup. ([Dramatiq][4])

# Step 13 — Containerize the full system

Once the main flow works locally, define:

* frontend container
* backend container
* worker container
* postgres container
* redis container
* minio container
* nginx container

Then add:

* `.env`
* local development compose file
* production compose file or Helm later

Do not delay containerization until the end. Do it once the first full slice works.
